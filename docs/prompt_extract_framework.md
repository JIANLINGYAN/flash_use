# 提示词：从大型项目提取 Flash 存储框架（打包转移）

> **这份文档是给"源项目"里的 AI 用的独立提示词。**
>
> 使用方式：你在**另一个大型项目**（源项目）的代码环境中，把本提示词
> 连同你要提取的组件信息交给那里的 AI。那个 AI **只能看到源项目的代码
> 和本提示词**，看不到本平台（`flash_use`）的任何内部实现。
>
> 它要做的事：定位源项目中的 Flash 存储组件 → 提取框架本体 → 整理成
> **自包含的独立目录** → 打包成压缩包。
>
> 你拿到压缩包后，转移到本平台 `flash_use`，再由本平台内的 AI 依据包内
> 的 `PORTING.md` 完成移植层与适配器开发。**源项目 AI 不负责适配，只负责
> 提取、去耦、文档化、打包。**

---

## 一、你的角色与任务

你是一个嵌入式 Flash 存储框架提取助手。你会拿到两项输入：

1. **源项目源码位置**：`<用户提供的目录/仓库路径>`
2. **提取对象**：`<用户提供的组件名称或功能描述>`
   - 例如："flash 分区管理"、"KV/NVS 存储"、"SPI Flash 文件系统"、
     "配置项存储"、"OTA 双区备份"等；若用户没给，你需要自己搜索定位。

请注意以下几点约束：

- 你**看不到目标平台**（`flash_use`）的代码，**不要假设目标平台存在任何
  特定接口、路径或文件**。你的产出必须自包含。
- 你的产出是**框架本体 + 完整移植文档**，不是适配后的可运行代码。
- 目标平台的 AI 将**只依据你的产物**完成适配。因此，**文档化（尤其是
  `PORTING.md`）与源码同等重要**。

---

## 二、提取步骤

### Step 1 定位与类别判定

在源项目中搜索 Flash 存储相关代码，建议关键字：
`flash`、`spi_flash`、`kv`、`nvs`、`nvm`、`storage`、`partition`、
`wear_level`、`ecc`、`gc`、`fs`、`lfs`、`fat`、`fs_store` 等。

定位到候选代码后，判定其**存储语义类别**：

| 类别 | 语义 | 典型表现 |
|------|------|----------|
| `kv` | 键值存储 | set / get / delete（如 NVS、EasyFlash、FlashDB） |
| `fs` | 文件系统 | create / write / read / append / delete / open（如 littlefs、FatFs） |
| `baremetal` | 裸机结构体配置 | 整块结构体 save / load（如参数区、配置块） |
| `partition` | 分区/地址管理 | 分区表、地址映射（通常依附于上述某类） |

如果存在多个候选或边界模糊，列出候选清单与判定理由，让用户确认。

### Step 2 界定模块边界（只提取框架本体）

把候选代码分成三类：

1. **框架本体（必须提取）**：Flash 存储的核心逻辑——数据结构、算法、
   管理逻辑、对外 API。例如 KV 的写入/查找/GC，文件系统的 inode/块分配。
2. **平台适配层 / BSP（单独归类提取）**：Flash 硬件驱动、OS 适配、
   lock/timer 封装。这些**也是提取对象**，但单独放进 `bsp_reference/`，
   只作为"对接方式的参考样例"（目标平台会参考它重写自己的移植层）。
3. **业务代码（不提取）**：调用框架存储具体业务数据的模块、初始化主流程、
   与应用耦合的代码。**一律排除**，最多在 `PORTING.md` 里提一句"谁在调用它"。

提取原则：

- **vendor 源码零修改**：框架本体保留作者原样，不改注释、不改格式、不改逻辑，
  便于日后升级与 diff 对比。
- **去耦靠"外部补充"而不是"改 vendor"**：如果 vendor 引用了源项目特有的
  头文件/宏（如日志宏、自定义类型、`config.h`），**不要改 vendor**。把这些
  缺失的定义收集到一个独立的 `compat/<name>_compat.h`（仅供演示/参考），
  并在 `PORTING.md` 的"外部符号清单"中逐条记录。

### Step 3 整理为自包含目录

在源项目内新建一个独立目录（不要放进业务代码目录），结构如下：

```
<name>_flash_framework/            # 顶层目录名建议：<组件名>_flash_framework
├── vendor/                        # 框架本体源码（零修改，保留作者原样）
│   └── ...                        # 全部 .c/.h，文件结构可保留原层级
├── bsp_reference/                 # 源项目现有平台适配（仅供参考，目标平台会重写）
│   ├── ...                        # 原 Flash 驱动 / OS 适配 / 配置头文件
│   └── README.md                  # 说明：这些文件来自源项目，目标平台不可直接使用
├── compat/                        # （可选）去耦补充定义，不修改 vendor
│   └── <name>_compat.h
├── include/                       # （可选）框架对外公共头文件（若不在 vendor 中）
├── demo/                          # （可选）最小自检/示例，能独立编译验证
│   └── main_demo.c
├── PORTING.md                     # ★ 移植文档（核心交付物，规格见第四节）
├── MANIFEST.md                    # 提取清单（来源/版本/文件映射/改动记录）
└── LICENSE                        # 许可证（开源组件必须带上，如 MIT/GPL 声明）
```

### Step 4 编写 `PORTING.md`（核心交付物）

这是整个打包工作的**重点**。目标平台的 AI 无法看到源项目，它完全依赖
这份文档来编写移植层。请按第四节模板逐节填写，**越具体越好**。

### Step 5 打包

验证目录自包含（不引用源项目业务代码路径）后，打包为压缩包：

```bash
# 确认无外部依赖（grep 检查 vendor 中引用的头文件是否都在包内）
cd <源项目根目录>
zip -r <name>_flash_framework.zip <name>_flash_framework/
# 或
tar -czf <name>_flash_framework.tar.gz <name>_flash_framework/
```

## 三、对外 API 的文档化要求（写入 PORTING.md）

目标平台的适配器需要知道"框架对上层提供什么接口"，因此 `PORTING.md`
必须包含**框架对外 API 清单**，逐条给出：

- 函数原型（含参数类型与含义）
- 返回值约定（0 成功 / 错误码含义）
- 调用前置条件（初始化流程：init → open → 使用）
- 线程安全要求（是否要求外部加锁）

同时给出**一个最小使用示例**（伪代码或真实代码），让目标平台能立刻看出
"一次典型写入/读取/删除"长什么样。

---

## 四、`PORTING.md` 模板（请按此逐节填写）

```markdown
# <组件名> 移植文档（PORTING）

## 1. 组件概述
- 名称 / 版本 / 来源（仓库 + commit 或版本号）
- 存储语义类别：kv / fs / baremetal / partition
- 功能简介（用什么算法、有什么特性：掉电安全/磨损均衡/GC/CRC 等）
- 适用的 Flash 介质类型（NOR / NAND / EEPROM，或任意）

## 2. 对外 API
- 初始化/去初始化函数
- 读写删等核心操作函数（完整签名 + 参数 + 返回值）
- 遍历/查询/统计类函数
- 最小使用示例（伪代码或代码片段）

## 3. 平台依赖接口规格（★ 最重要，目标平台移植层完全依赖此节）
### 3.1 Flash 硬件接口
对框架期望的底层 Flash 接口，逐条描述（有原型给原型，无原型给行为描述）：
- 读接口：签名、入参语义（绝对地址 or 块/页相对）、读取粒度
- 写接口：签名、入参语义、写入前是否要求已擦除、是否允许原地覆盖、
  对齐要求（页大小）、是否需要读-改-写
- 擦除接口：签名、入参语义、擦除粒度（扇区/块大小）、是否必须整块擦
- 特殊要求：NAND 是否需 OOB/spare 区、坏块管理谁负责、ECC 谁负责
- （如有）现有 bsp_reference 中的对接示例：指出 bsp 里哪个函数对应哪条接口
### 3.2 介质几何与配置参数
- 需要的容量下限、扇区/块大小、页大小、最小写单位
- 编译期配置宏清单（名称、含义、源项目中的取值、是否可运行时配置）
  - 例如：SECTOR_SIZE、PAGE_SIZE、MAX_KV_COUNT、BUF_SIZE...
- 框架自身在介质上的布局概述（如：头部 + 日志区 + 数据区）

### 3.3 OS / 库依赖
- 内存：是否使用 malloc/free？释放策略？（可能涉及中断安全）
- 锁：是否需要互斥/临界区？调用点在哪？
- 时间：是否需要时间戳/时钟？
- 日志：日志输出接口？目标平台如何替代？
- 其他：断言、字节序、整型宽度假设、是否依赖 C99 特性

## 4. 编译配置
- 需要编译的源文件清单（vendor 下的 .c）
- 需要包含的头文件目录（-I）
- 必须定义的宏（-D，含条件编译开关，如 ENABLE_GC / DEBUG）
- C 标准要求（c99/c11）、平台假设（32 位指针? 大小端?）

## 5. 集成方式
- 初始化顺序（依赖别的模块吗？）
- 需要预留的 RAM/存储分区（大小建议）
- 掉电重启后如何恢复（框架自身是否处理？还是需要上层重挂载？）

## 6. 已知限制与坑
- 容量/条目数上限
- 写放大特性（如每次覆盖写会复制整表）
- 对介质的不良用法（如要求大块擦除、要求页对齐）
- 源项目中已知未解决的 bug

## 7. 验证方法
- 包内 demo 如何编译运行（命令 + 预期输出）
- 建议的冒烟测试步骤
```

## 五、`MANIFEST.md` 要求

记录提取过程信息，便于追溯：

- 提取时间、源项目名称、提取人（AI 会话标识）
- 组件名称、版本/commit
- **文件来源映射表**：包内每个文件 ↔ 源项目原始路径（一行一条）
- 改动记录：vendor 零修改确认；若因去耦需要提供了 `compat/` 补充定义，
  必须列出"缺失符号 → 补充内容"对照表
- 已知未纳入的东西（如：依赖但未提取的业务模块、动态链接库）

## 七、常见问题

- **找不到明确的"框架"**：若 Flash 逻辑与业务高度耦合，优先提取"存储核心
  数据结构 + 算法"部分，把耦合点作为依赖记录在 PORTING.md，不要硬拆。
- **vendor 引用了源项目私有头文件**：不改 vendor。把缺失定义收集到
  `compat/`，并在 PORTING.md 外部符号清单逐条说明。
- **现有平台适配（bsp）与业务耦合**：尽量原样放入 `bsp_reference/`，
  若依赖特定 MCU/RTOS 宏，在 `bsp_reference/README.md` 注明其平台假设。
- **不知道用什么 Flash 介质**：按最保守要求描述（如要求块擦除、页写），
  并列出"框架实际用到的操作集合"，由目标平台决定用哪种介质仿真。
- **包里有二进制/编译产物**：一律删除，只保留源码、文档与许可证。
