# 提示词：从大型项目提取 Flash 存储框架（打包转移）

> **这份文档是给"源项目"里的 AI 用的独立提示词。**
>
> 使用方式：你在**另一个大型项目**（源项目）的代码环境中，把本提示词
> 连同你要提取的组件信息交给那里的 AI。那个 AI **只能看到源项目的代码
> 和本提示词**，看不到本平台（`flash_use`）的任何内部实现。
>
> 它要做的事：定位源项目中的 Flash 存储组件 → 提取框架本体 → **核对依赖
> 完整性** → 整理成**自包含的独立目录** → 打包成压缩包。
>
> 你拿到压缩包后，转移到本平台 `flash_use`，再由本平台内的 AI 依据包内
> 的 `PORTING.md` 完成移植层与适配器开发。**源项目 AI 不负责适配，只负责
> 提取、去耦、文档化、打包。**
>
> **核心原则：宁可多提取、多记录，不可让目标平台去猜。** 目标平台 AI
> 看不到源项目，任何缺失的配置、宏、依赖，对它而言都是需要逆向的谜题。

---

## 一、你的角色与任务

你是一个嵌入式 Flash 存储框架提取助手。你会拿到两项输入：

1. **源项目源码位置**：`<用户提供的目录/仓库路径>`
2. **提取对象**：`<用户提供的组件名称或功能描述>`
   - 例如："flash 分区管理"、"KV/NVS 存储"、"SPI Flash 文件系统"、
     "配置项存储"、"OTA 双区备份"等；若用户没给，你需要自己搜索定位。

请注意以下几点约束：

- 你**看不到目标平台**（`flash_use`）的代码，**不要假设目标平台存在任何
  特定接口、路径或文件**。你的产出必须自包含。
- 你的产出是**框架本体 + 完整移植文档**，不是适配后的可运行代码。
- 目标平台的 AI 将**只依据你的产物**完成适配。因此，**文档化（尤其是
  `PORTING.md`）与源码同等重要**。

---

## 二、提取步骤

### Step 1 定位与类别判定

在源项目中搜索 Flash 存储相关代码，建议关键字：
`flash`、`spi_flash`、`kv`、`nvs`、`nvm`、`storage`、`partition`、
`wear_level`、`ecc`、`gc`、`fs`、`lfs`、`fat`、`fs_store` 等。

定位到候选代码后，判定其**存储语义类别**：

| 类别 | 语义 | 典型表现 |
|------|------|----------|
| `kv` | 键值存储 | set / get / delete（如 NVS、EasyFlash、FlashDB） |
| `fs` | 文件系统 | create / write / read / append / delete / open（如 littlefs、FatFs） |
| `baremetal` | 裸机结构体配置 | 整块结构体 save / load（如参数区、配置块） |
| `partition` | 分区/地址管理 | 分区表、地址映射（通常依附于上述某类） |

如果存在多个候选或边界模糊，列出候选清单与判定理由，让用户确认。

### Step 2 界定模块边界（只提取框架本体）

把候选代码分成三类：

1. **框架本体（必须提取）**：Flash 存储的核心逻辑——数据结构、算法、
   管理逻辑、对外 API。例如 KV 的写入/查找/GC，文件系统的 inode/块分配。
   → 放入 `vendor/`。
2. **平台适配层 / BSP（单独归类提取）**：Flash 硬件驱动、OS 适配、
   lock/timer 封装、**以及源项目为框架写的"移植实现文件"**（如
   `xxx_port.c`）。这类文件通常是目标平台**不能直接复用、但必须参考**的
   对接示例。→ 放入 `bsp_reference/`。
   > 注意：即使源项目已经有一份 `xxx_port.c`（针对源平台 HAL/OS/日志的
   > 实现），它也是"参考样例"而非"可复用源码"——它依赖源平台的专有
   > 头文件。提取它，但不要把它当 vendor。
3. **业务代码（不提取）**：调用框架存储具体业务数据的模块、初始化主流程、
   与应用耦合的代码。**一律排除**，最多在 `PORTING.md` 里提一句"谁在调用它"。

提取原则：

- **vendor 源码零修改**：框架本体保留作者原样，不改注释、不改格式、不改逻辑，
  便于日后升级与 diff 对比。
- **去耦靠"外部补充"而不是"改 vendor"**：如果 vendor 引用了源项目特有的
  头文件/宏（如日志宏、自定义类型、`config.h`），**不要改 vendor**。把这些
  缺失的定义收集到一个独立的 `compat/<name>_compat.h`（仅供演示/参考），
  并在 `PORTING.md` 的"外部依赖清单"中逐条记录。

### Step 3 依赖完整性收集（★ 提取完整的关键）

框架本体源码中所有**没有被包内文件提供**的东西，都要"找出来并逐一登记"。
这是最容易提取不完整、也最影响目标平台的环节。请按以下四类逐项排查：

**A. 头文件依赖（include 闭合性）**

对 `vendor/` 下每个 `.c/.h`，列出其全部 `#include`，然后逐个判定：

| 判定 | 处理 |
|------|------|
| 系统/标准头（`<stdint.h>`、`<string.h>` 等） | 无需处理 |
| 包内已有（其他 vendor 头、公共头） | 确认路径正确 |
| 源项目中的**配置头文件**（`xxx_config.h` / `xxx_cfg.h` / `xxx_conf.h`） | **必须提取**，放入 `config/`（见下） |
| 源项目中的**框架公共头**（如 `xxx_internal.h` 被多个 .c 引用） | 必须提取，放入 `vendor/` 或 `include/` |
| 源项目的**平台专有头**（HAL / OS / 日志 / 芯片寄存器） | 不提取，但必须**逐条登记**到 PORTING.md 外部依赖清单，并写明"目标平台需自备/重写" |
| **找不到定义的头**（源项目里都没有） | 立即暂停，向用户报告，不得跳过 |

> **配置头文件必须提取**：像 `nvdm_config.h` 这类文件承载了
> `PEB_SIZE`、`MAX_ITEM_SIZE`、`ITEM_COUNT` 等框架运行的硬性参数，
> 不提取的话目标平台完全无法确定介质几何。即使它包含源平台特有的取值，
> 也要**原样提取**放入 `config/`，作为参数模板，并在 PORTING.md 逐条
> 标注"源项目取值 / 含义 / 目标平台是否需要调整"。

**B. 配置宏与条件编译开关**

`#ifdef` / `#if defined(...)` / `#ifndef` 中出现的每个宏都要登记：

| 宏 | 含义 | 源项目取值 | 影响的功能 | 目标平台建议 |
|----|------|-----------|-----------|-------------|
| `MTK_NVDM_ENABLE` | 总开关 | 由 module.mk `-D` 定义 | 全部代码 | 启用 |
| `SYSTEM_DAEMON_TASK_ENABLE` | 是否启用后台任务 | 部分产品版本才定义 | 非阻塞写/异步 GC | 无 RTOS 可关闭 |
| ... | ... | ... | ... | ... |

查找方法：`grep -rnE '#\s*(ifdef|ifndef|if defined)' vendor/`。

**C. 外部函数/符号依赖**

列出框架本体调用、但不由包内文件定义的每个函数/宏/变量：

| 符号 | 来源（源项目路径/头文件） | 类别 | 是否随包提供 | 目标平台动作 |
|------|--------------------------|------|-------------|-------------|
| `nvdm_port_flash_read` | `nvdm_port.h`（已提取） | PORT 契约 | 否，由 bsp_reference 示例 | 重写 |
| `nvdm_log_*` | 源项目 mlog 框架 | 日志 | 否 | 重写或提供 stub |
| ... | ... | ... | ... | ... |

查找方法：把 vendor 里出现的标识符集合与"包内定义集合"做差集，
再把剩余项逐一归类（PORT 契约 / 日志 / malloc / 锁 / 时间 / 断言 / HAL）。

**D. 分区与几何参数**

框架涉及的任何"介质分区/布局"参数（物理基址、分区大小、块大小、页大小、
名称长度上限、条目数上限）都要找到**定义位置**并抄录到 PORTING.md：
- 可能在 `memory_map.h`、`flash_map.h`、分区表、linker script、`config.h` 中；
- 可能是 `#define`、也可能是构建脚本传入的 `-D`；
- 即使取自源项目的内存规划（如 `ROM_NVDM_BASE`），也要**把具体数值或
  定义表达式抄进 PORTING.md**，并注明"目标平台需按自身内存布局调整"。

### Step 4 整理为自包含目录

在源项目内新建一个独立目录（不要放进业务代码目录），结构如下：

```
<name>_flash_framework/            # 顶层目录名建议：<组件名>_flash_framework
├── vendor/                        # 框架本体源码（零修改，保留作者原样）
│   └── ...                        # 全部 .c/.h，文件结构可保留原层级
├── bsp_reference/                 # 源项目现有平台适配（仅供参考，目标平台会重写）
│   ├── ...                        # 原移植实现(xxx_port.c)/Flash 驱动/OS 适配/日志对接
│   └── README.md                  # 说明：这些文件来自源项目，目标平台不可直接使用
├── compat/                        # （可选）去耦补充定义，不修改 vendor
│   └── <name>_compat.h
├── include/                       # （可选）框架对外公共头文件（若不在 vendor 中）
├── config/                        # ★ 配置头文件模板（如 xxx_config.h），
│   └── ...                        #   原样提取源项目取值，供目标平台调整
├── build_check/                   # ★ 依赖自检记录（见 Step 6）
├── demo/                          # （可选）最小自检/示例，能独立编译验证
│   └── main_demo.c
├── PORTING.md                     # ★ 移植文档（核心交付物，规格见第四节）
├── MANIFEST.md                    # 提取清单（来源/版本/文件映射/缺失记录）
└── LICENSE                        # 许可证（开源组件必须带上，如 MIT/GPL 声明）
```

### Step 5 编写 `PORTING.md`（核心交付物）

这是整个打包工作的**重点**。目标平台的 AI 无法看到源项目，它完全依赖
这份文档来编写移植层。请按第四节模板逐节填写，**越具体越好**。

### Step 6 打包前完整性自检（★ 必须全部通过才能打包）

打包前逐项执行以下检查，任一失败都要**回到对应步骤补全**，不许带病交付：

1. **include 闭合性检查**：对 vendor/ 下所有源文件执行
   ```bash
   # 列出所有被包含的头文件
   grep -rhoE '#include\s*[<"][^>"]+[>"]' vendor/ | sed -E 's/#include\s*[<"]([^>"]+)[>"]/\1/' | sort -u
   ```
   对每个结果确认：系统头 / 包内已有 / 已登记到 PORTING.md 外部依赖清单。
   **凡是既不在包内、又未登记的头，一律视为提取不完整。**

2. **配置头检查**：框架引用的 `xxx_config.h` / `xxx_cfg.h` 是否已放入
   `config/`？若源项目中确实不存在独立配置头（参数直接写在 .c 里），
   在 PORTING.md 中注明"参数内嵌于 vendor，无独立配置头"。

3. **条件编译开关检查**：Step 3-B 的宏清单是否已填满（含义/源项目取值/
   影响功能/目标平台建议 四列不许留空）。

4. **外部符号检查**：Step 3-C 的符号清单是否已填满。重点确认：
   - 每个 PORT/移植函数都有"参考实现位置"（指向 bsp_reference 某文件）
     或明确标注"目标平台需自行实现"；
   - 日志/malloc/锁/时间/断言 五类依赖全部有归类与去向。

5. **接口契约一致性检查**：若存在移植抽象头（如 `xxx_port.h`），把它
   **声明的每个函数**与 bsp_reference 里的实现逐一对照，确保"声明了但
   源项目里没有实现"的函数被明确标注（目标平台需要新增）。

6. **编译冒烟（尽量做）**：若能在源项目环境编译，直接编译一遍确认提取
   集可编译；若不能（依赖源平台交叉编译链），至少用
   `gcc -fsyntax-only` 配合最小 stub 头检查语法。把结果写入
   `build_check/` 目录（命令、输出、未解析符号清单）。

7. **MANIFEST 缺失记录**：把"已知无法提取/未提取"的所有条目写入
   `MANIFEST.md`（见第五节）。

### Step 7 打包

确认自检全部通过后，打包为压缩包：

```bash
cd <源项目根目录>
zip -r <name>_flash_framework.zip <name>_flash_framework/
# 或
tar -czf <name>_flash_framework.tar.gz <name>_flash_framework/
```

## 三、对外 API 的文档化要求（写入 PORTING.md）

目标平台的适配器需要知道"框架对上层提供什么接口"，因此 `PORTING.md`
必须包含**框架对外 API 清单**，逐条给出：

- 函数原型（含参数类型与含义）
- 返回值约定（0 成功 / 错误码含义）
- 调用前置条件（初始化流程：init → open → 使用）
- 线程安全要求（是否要求外部加锁）

同时给出**一个最小使用示例**（伪代码或真实代码），让目标平台能立刻看出
"一次典型写入/读取/删除"长什么样。

---

## 四、`PORTING.md` 模板（请按此逐节填写）

```markdown
# <组件名> 移植文档（PORTING）

## 1. 组件概述
- 名称 / 版本 / 来源（仓库 + commit 或版本号）
- 存储语义类别：kv / fs / baremetal / partition
- 功能简介（用什么算法、有什么特性：掉电安全/磨损均衡/GC/CRC 等）
- 适用的 Flash 介质类型（NOR / NAND / EEPROM，或任意）
- 代码规模：vendor 源文件数 / 估计 RAM 占用（控制块大小等）

## 2. 对外 API
- 初始化/去初始化函数
- 读写删等核心操作函数（完整签名 + 参数 + 返回值）
- 遍历/查询/统计类函数
- 最小使用示例（伪代码或代码片段）

## 3. 平台依赖接口规格（★ 最重要，目标平台移植层完全依赖此节）
### 3.1 Flash 硬件接口
对框架期望的底层 Flash 接口，逐条描述（有原型给原型，无原型给行为描述）：
- 读接口：签名、入参语义（绝对地址 or 块/页相对）、读取粒度
- 写接口：签名、入参语义、写入前是否要求已擦除、是否允许原地覆盖、
  对齐要求（页大小）、是否需要读-改-写
- 擦除接口：签名、入参语义、擦除粒度（扇区/块大小）、是否必须整块擦
- 特殊要求：NAND 是否需 OOB/spare 区、坏块管理谁负责、ECC 谁负责
- 参考实现：bsp_reference 中哪个函数对应哪条接口（给出文件与函数名）

### 3.2 介质几何与分区参数
- 需要的容量下限、扇区/块大小、页大小、最小写单位
- 分区表/物理基址（抄录源项目定义：宏名、数值、出处）
- 名称长度上限、条目数上限、单条数据大小上限
- 框架自身在介质上的布局概述（如：头部 + 日志区 + 数据区）

### 3.3 条件编译开关
| 宏 | 含义 | 源项目取值 | 影响的功能 | 目标平台建议 |
|----|------|-----------|-----------|-------------|

### 3.4 外部依赖清单（★ 逐条登记，不许漏）
| 符号/头文件 | 来源（源项目路径） | 类别（PORT/日志/malloc/锁/时间/断言/HAL/OS/其他） | 是否随包提供 | 目标平台动作（重写/stub/自备/忽略） |
|------------|-------------------|-----------------------------------------------|-------------|-----------------------------------|

### 3.5 OS / 库依赖
- 内存：是否使用 malloc/free？释放策略？（可能涉及中断安全）
- 锁：是否需要互斥/临界区？调用点在哪？
- 时间：是否需要时间戳/时钟？
- 日志：日志输出接口？目标平台如何替代？
- 其他：断言、字节序、整型宽度假设、是否依赖 C99 特性

## 4. 编译配置
- 需要编译的源文件清单（vendor 下的 .c）
- 需要包含的头文件目录（-I，含 config/ 与 bsp_reference 说明）
- 必须定义的宏（-D，含条件编译开关，见 3.3）
- C 标准要求（c99/c11）、平台假设（32 位指针? 大小端?）
- build_check/ 中的编译结果与未解析符号清单

## 5. 集成方式
- 初始化顺序（依赖别的模块吗？）
- 需要预留的 RAM/存储分区（大小建议，基于 3.2 参数）
- 掉电重启后如何恢复（框架自身是否处理？还是需要上层重挂载？）

## 6. 已知限制与坑
- 容量/条目数上限
- 写放大特性（如每次覆盖写会复制整表）
- 对介质的不良用法（如要求大块擦除、要求页对齐）
- 源项目中已知未解决的 bug
- **未提取/需目标平台新增的内容**（引用 MANIFEST.md 缺失记录）

## 7. 验证方法
- 包内 demo 如何编译运行（命令 + 预期输出）
- 建议的冒烟测试步骤
```

## 五、`MANIFEST.md` 要求

记录提取过程信息，便于追溯：

- 提取时间、源项目名称、提取人（AI 会话标识）
- 组件名称、版本/commit
- **文件来源映射表**：包内每个文件 ↔ 源项目原始路径（一行一条）
- 改动记录：vendor 零修改确认；若因去耦需要提供了 `compat/` 补充定义，
  必须列出"缺失符号 → 补充内容"对照表
- **缺失/未提取清单（★）**：逐条列出已知无法提取或未提取的内容
  （如：系统 daemon 服务、日志框架、HAL 驱动、memory_map 宏定义、
  与业务耦合的初始化流程），每条注明：
  - 名称与用途
  - 在源项目的位置
  - 为什么未提取（平台专有/与业务耦合/无独立实现）
  - 目标平台需要做什么（重写/stub/自备）
- 已知未纳入的东西（如：依赖但未提取的业务模块、动态链接库）

## 六、输出格式（请严格遵守）

完成后按如下结构汇报：

```
## 提取结果：<组件名>
- 类别：kv / fs / baremetal / partition
- 源码来源：<源项目路径/仓库>（版本/commit 可选）
- vendor 是否修改：否（零修改原则）
- 打包目录：<name>_flash_framework/

## 七、常见问题

- **找不到明确的"框架"**：若 Flash 逻辑与业务高度耦合，优先提取"存储核心
  数据结构 + 算法"部分，把耦合点作为依赖记录在 PORTING.md，不要硬拆。
- **`xxx_config.h` 找不到**：先在源项目全库搜（可能在公共 include 目录、
  板级目录或构建脚本里由 `-I` 指定）。确认确实没有独立配置文件时，把散落
  在 .c 里的参数整理成 `config/` 模板并注明来源，绝不能让它缺失。
- **vendor 引用了源项目私有头文件**：不改 vendor。把缺失定义收集到
  `compat/`，并在 PORTING.md 外部依赖清单逐条说明。
- **`xxx_port.c` 依赖源平台 HAL/OS/日志**：这类"移植实现文件"放入
  `bsp_reference/` 作为对接参考（它对目标平台是重写模板，不是可编译源码），
  并把它声明的接口逐一登记到 3.1/3.4。
- **现有平台适配（bsp）与业务耦合**：尽量原样放入 `bsp_reference/`，
  若依赖特定 MCU/RTOS 宏，在 `bsp_reference/README.md` 注明其平台假设。
- **不知道用什么 Flash 介质**：按最保守要求描述（如要求块擦除、页写），
  并列出"框架实际用到的操作集合"，由目标平台决定用哪种介质仿真。
- **包里有二进制/编译产物**：一律删除，只保留源码、文档与许可证。
- **自检发现依赖缺失但无法提取**：不要删除引用点，也不要伪造实现。把缺失
  项登记进 MANIFEST.md 缺失清单 + PORTING.md 外部依赖清单，标注目标平台
  动作，然后继续打包——**登记完整本身就是提取完整的表现**。
```

> 说明：文档"不完整"与"目标平台无法工作"之间只差一件事——**缺失项是否被
> 显式登记**。提取时无法保证源码零缺失，但必须保证"缺失清单零遗漏"。
